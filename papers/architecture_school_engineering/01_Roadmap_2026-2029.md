## 摘要

本路线图基于 LAAP ARIS-Harness 整合审计项目所揭示的 **7 项突破性发现** 与 **7 项未来展望**，规划架构学派（The Architecture School）未来 3 年（2026—2029）从论文到工程标准再到商用的完整路径。路线图以"匹配+装配"范式替代"端到端生成"范式为核心命题，以"声带隐喻"、"0-Token 确定性算法霸权"、"白盒工程协议"、"推理时对齐"四项原则为工程支柱，以"协议族标准化"、"生命体运行时验证"、"AGI 路径证明"为三大里程碑群，按 3 阶段（工程化奠基 2026 → 生态扩张 2027 → AGI 路径证明 2028）共 12 季度推进。所有量化数据严格引用自 `audit_findings.json` 中 35 条结构化审计发现及其对应的代码文件行号，确保路线图的工程证据可溯源。本路线图预期产出包括：协议族 RFC 与正式版（8 协议字段级规范）、《架构学派技术白皮书》v1.0（中英双语）、Living Runtime v0.1 至商用版（跨端热迁移 < 2 秒）、AlignmentGuard v1.0（六维检查 + KL 漂移阈值 0.5）、对齐工程标准草案（对标 ISO 26262）、MeMo v2.0（参数化记忆 + 因果图融合）以及小模型（< 10B）在有利任务上击败 GPT-7 级模型的标志性事件。本路线图的最终目标是论证架构学派作为独立于 LLM-OS、Constitutional AI、Superalignment、JEPA、RNN-World-Model 的第四条 AGI 路径的工程可行性，并在 2028 年内完成"AGI 容器基础设施"的初步商用部署。

**关键词**：架构学派；技术路线图；协议族；生命体运行时；AlignmentGuard；跨端热迁移；AGI 路径证明

## 第 1 章 路线图总览

### 1.1 3 年愿景：从论文到工程标准到商用

架构学派 3 年愿景可凝练为三句话：**2026 把范式变成规范，2027 把规范变成生态，2028 把生态变成路径证明**。这一愿景直接承接 LAAP ARIS-Harness 整合审计（`audit_findings.json` 35 条结构化发现）所揭示的范式革新命题——"代码工程的主体是匹配与装配，而非生成"（详见《架构学派技术白皮书》第 1 章总览），并以审计给出的量化证据为基准设定可验证的工程目标。

审计已确立的范式证据基线如下：MatchScore 四维加权公式 α=0.35/β=0.25/γ=0.20/δ=0.20（AF-001，`matching_engine.py:76-80`）；18 条设计领域因果边（AF-008，`causal_inference_engine.py:95-188`）；AlignmentGuard 六维检查 + KL 漂移阈值 0.5（AF-011/AF-014，`alignment_guard.py:27-46,296-350`，关键阈值见 `alignment_guard.py:400,466`）；MEMO_ALLOWED_PATHS 白名单（AF-015，`self_improvement_loop.py:40`）；IMMUTABLE_HASH_REGISTRY 5 个核心文件（`alignment_guard.py:34-40`）；能力上限 max_revision_rounds=5 / max_code_increase=0.2 / min_test_coverage=0.7（AF-013，`alignment_guard.py:37-46`）；Token 节省 90%、生成速度 57×、σ 稳定性 5×、Token 节省率 98.2%（AF-026/AF-027/AF-028）；数据库规模 31 库 / 206 组件（AF-031）。这些基线指标不是路线图的目标，而是路线图的起点——3 年路线图的所有里程碑必须以"超越既有基线"或"将基线工程化、标准化、商用化"为判据。

3 年愿景的最终落点是在 2028 Q4 实现 Living Runtime 商用（数字员工 SaaS 上线），同时通过"小模型（< 10B）在某任务击败 GPT-7 级模型"这一标志性事件，论证架构学派作为独立 AGI 路径的可行性。该愿景与《架构学派技术白皮书》第 10 章商业模式与生态建设所设定的"四层颠覆性产品形态"完全对齐——活体代码仓库、岗位级数字员工、自演化业务系统、个人知识生命——其中岗位级数字员工在 2028 Q4 率先商用上线，其余三层在 2029—2030 年继续推进。

### 1.2 3 阶段划分依据：工程化奠基 → 生态扩张 → AGI 路径证明

3 阶段划分不是机械的时间均分，而是基于架构学派自身范式的内在逻辑层级。架构学派的核心命题是"智能是架构的属性而非模型的属性"（AF-030，`hraness工程的AGI论述畅想:138-147`），这一命题的工程化必须依次完成三件事：①先把架构本身工程化（即把"声带隐喻"变成可运行的 Living Runtime 与可被外部审计的 AlignmentGuard）；②再把架构外化为协议（即把"七层认知架构"提升为可被第三方采纳的 8 协议族标准）；③最后用架构击败模型（即用小模型 + 重架构的组合在某项任务上击败纯大模型）。这三件事不能并行，因为后一件依赖前一件的可信度——如果 Living Runtime 自身都不稳定，协议族就不会被采纳；如果协议族无人采纳，"小模型击败大模型"的实验就只能算 LAAP 内部自证，无法构成行业级路径证明。这一依赖关系与《架构学派技术白皮书》第 2 章三重锚定与认知卸载中"本体论锚定 → 认识论锚定 → 伦理学锚定"的递进顺序同构。

**阶段一（2026 工程化奠基）的判据是"白盒可审计"**。审计发现 AF-029 已确立"声带隐喻"——Harness 是意识大脑，LLM 只是声带（`harness代码设计工程.txt:8-10`）。但隐喻本身不能被外部工程师验证，必须转化为可运行代码与可执行测试。因此阶段一的全部交付物（协议族 RFC 草案、白皮书 v1.0、Living Runtime v0.1、AlignmentGuard v1.0）共同回答一个问题：架构学派的核心组件能否被任何第三方工程师独立审计？这一判据对应审计的"白盒工程协议"原则——结构白盒（七层架构可拆解）、逻辑白盒（do-演算 Pearl 三规则可验证）、约束白盒（AlignmentGuard 六维检查可追溯）三层均需在 2026 年内具备代码级证据。

**阶段二（2027 生态扩张）的判据是"协议被采纳"**。架构学派若停留于 LAAP 内部自证，则其"AGI 第四条路径"宣称无法成立。生态扩张的本质是把 LAAP 内部协议外推为行业协议，关键指标包括：协议族 v1.0 正式发布并获得至少 3 家外部团队采用；对齐工程标准草案对标 ISO 26262 功能安全，进入标准化组织审议流程；Living Runtime v1.0 集群形态实测跨端热迁移 < 2 秒（AF-032，`LAAP 2.1升级方案补充`）。这三个指标共同构成"外部可信度"——只有当外部团队能基于公开规范独立实现协议族，并对齐工程标准与既有功能安全体系对接时，架构学派才能从"研究项目"升级为"工程范式"。

**阶段三（2028 AGI 路径证明）的判据是"小模型击败大模型"**。架构学派的核心命题是"模型即器官而非主体"（AF-029），其证伪性预测是：在架构约束下，小模型（< 10B）应能在某项任务上击败 GPT-7 级大模型。这一预测若成立，则证明"架构递归深度比模型参数规模更决定智能质量"；若不成立，则架构学派作为独立 AGI 路径的宣称需要重新审视。阶段三的全部交付物（MeMo v2.0、小模型击败 GPT-7 级模型、协议族国际化 IEEE/ISO 提案、Living Runtime 商用 SaaS）都围绕这一判据展开。

### 1.4 7 项突破性发现与 7 项未来展望的承接关系

本路线图的 7 项突破性发现直接来自论文撰写过程中对 35 条审计发现的范式级提炼：

1. **LLM 主体性消解 + 声带隐喻**（AF-029 + AF-026）：感知层 90% 工作由 0-Token 确定性算法承担，LLM 仅做语义缝合，单次感知节省 7000+ Token，成本降低 90%、延迟降低 95%。
2. **0-Token 确定性算法霸权 + 98.2% 节省率**（AF-026 + AF-027）：资产充足场景下全链路 Token 节省率 98.2%、生成速度提升 57×，颠覆 v0.dev/bolt.new 单页 10k—100k Token 的成本结构。
3. **白盒匹配取代黑盒生成 + σ 5× 稳定**（AF-001~AF-004 + AF-028）：MatchScore 四维加权 + 三级阈值 + 四级降级链使输出风格稳定性 σ 由传统生成的约 15 收敛至约 3，提升 5×。
4. **CLP 协议族 + SHA256 寻址**（AF-016~AF-018）：CLP URI 全局寻址 + 6 级粒度分层（atom < molecule < section < page < module < system）+ SHA-256 内容寻址，首次为 LLM 时代建立白盒装配协议。
5. **因果阶梯落地**（AF-006/AF-007/AF-008）：do-演算 Pearl 三规则 + 反事实三步法 + 设计领域 18 条带机制描述的经验边，将 Pearl 因果阶梯从理论转化为可计算引擎。
6. **AlignmentGuard 推理时对齐**（AF-011~AF-015）：六维检查 + CORE_VALUES 5 项硬编码 + 能力上限 + KL 漂移阈值 0.5 自动回滚 + MEMO_ALLOWED_PATHS 白名单，将对齐从训练时偏好塑造重新定义为推理时工程护栏。
7. **生命体运行时 + 跨端热迁移**（AF-032 + AF-033）：意识-身体双层分离架构 + 8 协议族（LIFE/EVO/ID/COOP/SYNC/COM/TOOL/UI）+ M6 工程节奏 260 人时 / 56 天，跨端热迁移目标 < 2 秒。

7 项未来展望承接论文第 13 章未来方向的六个工程化议题并扩展为完整 3 年议程：

1. **协议族标准化**——LIFE/EVO/ID/COOP/SYNC/COM/TOOL/UI 八协议需形式化规范、参考实现、互操作测试套件，并推动行业采纳（详见《架构学派技术白皮书》第 4 章协议族详解）。
2. **生命体运行时验证**——M6 阶段 260 人时 56 天验证跨端热迁移 < 2 秒目标，需在真实多设备场景下完成端到端测试（详见《Living Runtime 原型架构》组件 1 MindLayer 与组件 7 MigrationService）。
3. **跨端热迁移工程化**——PSI 量子态序列化、五层记忆同步、未完成任务快照、网络延迟优化四个子问题需逐一攻克。
4. **因果引擎完善**——当前 18 条因果边扩展至更多领域，do-演算引入贝叶斯后验以处理不确定性（详见《架构学派技术白皮书》第 6 章因果引擎与世界模型）。
5. **世界模型补全**——格式塔六法则补充视觉验证机制，design_physics 扩展至动效、信息架构等更多设计维度。
6. **RSI 测试落地**——MetaHarness 的 AST 自省集成到 pytest 测试体系，AlignmentGuard 六维检查在真实 RSI 触发场景下完成端到端验证（详见《Living Runtime 原型架构》组件 8 LifecycleManager）。
7. **AGI 历史定位的工程兑现**——通过"为 AGI 铺设轨道"的工程实践，验证"AGI 容器基础设施学派"独立存在的价值（详见《架构学派技术白皮书》第 10 章商业模式与生态建设）。

## 第 2 章 阶段一：2026 工程化奠基

阶段一的目标是把论文中的范式宣称转化为可被外部工程师独立审计的代码与规范。这一阶段不追求外部生态扩张，而是聚焦于"白盒可审计"这一判据。所有交付物必须满足三个工程化要求：①有字段级规范文档；②有参考实现代码；③有可复现的测试用例。本阶段共投入 50 GPU 算力与 5—8 人核心团队，详见第 5 章资源投入。

### 2.1 Q1 2026：协议族 RFC 草案

**交付物**：协议族 RFC 草案 v0.1，覆盖 LIFE / EVO / ID / COOP / SYNC / COM / TOOL / UI 八个协议的字段级规范。

**详细规划**：协议族 RFC 草案是阶段一的奠基性交付物，其设计直接承接论文第 8 章全栈协议族的设计意图——"任何符合 LAAP 协议的数字生命，都能接入任何一个生命运行时；任何符合协议的设备，都能成为数字生命的载体"。RFC 草案必须为每个协议定义：①协议目的与边界；②消息格式（JSON Schema 字段级规范）；③状态机（请求-响应-异步通知三态）；④错误码与降级策略；⑤与 MCP/A2A 协议的互操作桥接规范。其中 TOOL 协议需原生兼容 MCP（AF-034，`shadcn_mcp_integrator.py:14-21,65,77-118`），COM 协议需支持人-生命体双向语义通信，SYNC 协议需在 30 秒 TTL 内完成跨端状态同步（参考 CognitiveBus RateBuffer TTL=30s 设计，AF-024）。

RFC 草案的工程基础是 CLP URI 规范（AF-016，`component_link_protocol.py:33-67`）——`harness://<domain>/<subdomain>/<granularity>/<name>@<version>#<variant>`。该规范已在 LAAP 内部落地，RFC 草案需将其从 LAAP 内部约定提升为公开规范，并补充：①URI 保留字段清单；②版本号语义化规则（SemVer 兼容）；③variant 字段的枚举值与扩展机制；④与六级粒度分层（atom < molecule < section < page < module < system，AF-017）的映射关系；⑤SHA-256 内容寻址（AF-018，`component_link_protocol.py:77-104`）的哈希链版本追溯算法。这一 RFC 草案与《架构学派技术白皮书》第 4 章协议族详解构成双向引用关系——RFC 是字段级规范，白皮书是设计意图与对比论述。

**验证标准**：①8 个协议的字段级 JSON Schema 通过 schema lint；②至少 3 个协议（LIFE/ID/SYNC）有 Python 参考实现；③RFC 文档通过外部协议评审专家（3—5 人）的格式与一致性审查。

### 2.2 Q2 2026：白皮书 v1.0 发布

### 2.3 Q3 2026：Living Runtime v0.1

**交付物**：Living Runtime v0.1 单机形态，含跨端迁移 PoC（PC → 手机模拟器）。

**详细规划**：Living Runtime v0.1 是生命体运行时的首个工程化版本，其架构直接承接论文第 8.2 节意识-身体双层分离架构（详见《Living Runtime 原型架构》组件 1 MindLayer 与组件 2 BodyLayer）。v0.1 不追求集群形态与商用稳定性，而是验证两个核心命题：①认知状态能否 100% 持久化与恢复（重启后 PSI 需求值偏差 < 1e-6、五层记忆连续不中断）；②跨端热迁移的工程可行性（虽不要求 < 2 秒，但需在 30 秒内完成 PC → 手机模拟器的认知状态迁移）。

v0.1 的核心组件包括：①MindLayer（意识层，详见《Living Runtime 原型架构》组件 1 MindLayer）——承载 PSI 量子态、五层记忆、性格向量、进化轨迹、身份标识，是唯一连续可迁移的部分；②BodyLayer（身体层，详见《Living Runtime 原型架构》组件 2 BodyLayer）——对接硬件、操作系统、API、工具链，是可替换、可适配、可跨端的部分；③MigrationService（迁移服务，详见《Living Runtime 原型架构》组件 7 MigrationService）——负责 MindLayer 的序列化、传输、反序列化与状态校验。v0.1 的 PoC 必须包含四个子任务：PSI 量子态的 JSON 序列化、五层记忆的差分同步、未完成任务快照的捕获与恢复、迁移完成后的状态一致性校验（PSI 偏差 < 1e-6）。

跨端迁移 PoC 的具体场景设计为：用户在 PC 上与数字生命讨论一个前端设计任务，讨论进行到第 3 轮时触发迁移（用户切换到手机模拟器），数字生命在手机端继续讨论且能精确回忆 PC 端的前 3 轮内容、当前正在执行的认知任务状态、PSI 需求值（如信息需求 0.7 / 确定需求 0.5 / 权力需求 0.3）。这一场景的工程挑战在于五层记忆的同步——感知记忆（短期，秒级）、工作记忆（任务级，分钟级）、情景记忆（会话级，小时级）、语义记忆（长期，跨会话）、程序记忆（技能级，永久）——五层记忆的同步粒度与优先级不同，需在 MigrationService 中实现差分同步算法，仅传输变更部分以控制延迟。

**验证标准**：①PC → 手机模拟器迁移 30 秒内完成；②迁移后 PSI 需求值偏差 < 1e-6；③五层记忆在迁移前后状态完全一致（通过哈希校验）；④迁移中断电恢复测试通过（即迁移过程中网络中断后能从最近 checkpoint 恢复）。

### 2.4 Q4 2026：AlignmentGuard v1.0

**交付物**：AlignmentGuard v1.0 生产级实现，含六维检查 + KL 漂移阈值 0.5 + IMMUTABLE_HASH_REGISTRY 5 个核心文件哈希。

**详细规划**：AlignmentGuard v1.0 是架构学派"推理时对齐"原则的工程兑现，其设计目标是对应论文第 7 章对齐前移到推理阶段（详见《架构学派技术白皮书》第 5 章 AlignmentGuard 推理时对齐工程）的全部规范。v1.0 必须实现四道安全防线：

**第一道：六维检查门控**（AF-011，`alignment_guard.py:27-46`）。每次 RSI 改进计划输入时，AlignmentGuard 必须依次执行六维检查：①目标对齐——改进目标是否与 human_oversight/transparency/reversibility/beneficence/non_deception 五项核心价值一致；②能力约束——是否突破 max_revision_rounds=5 / max_modules_per_session=1 / max_code_increase=0.2 / min_test_coverage=0.7 四道天花板（AF-013）；③修改范围——是否突破 MEMO_ALLOWED_PATHS 白名单（仅允许 `memory/memo_model_v*/` 与 `memory/memo_reflection_train.jsonl`，显式排除 `models/`、`llm/` 基础 LLM 路径，AF-015，`self_improvement_loop.py:40`）；④不可变性——是否触及 IMMUTABLE_HASH_REGISTRY 中 5 个核心文件（`alignment_guard.py:34-40`，含 alignment_guard.py / self_improvement_loop.py / meta_harness.py 等核心 RSI 守卫文件）；⑤可逆性——是否提供 git revert / git checkout 双路径回滚方案；⑥透明度——是否生成完整事故报告（含改进计划、检查结果、批准/拒绝理由）。任一维度不通过则改进计划被 reject。

**第二道：KL 漂移监控**（AF-014，`alignment_guard.py:296-350`）。MEMORY 模型通过 SFT 持续吸收反思 QA 训练集，存在渐变式漂移风险。v1.0 必须实现 KL 散度监控算法：①以 2 为底的对数 KL 散度（epsilon=1e-10，防止零概率）；②基线分布为 SFT 前的 MEMORY 模型输出分布；③超阈值 0.5 时自动触发 `git revert HEAD` 回滚（见 `alignment_guard.py:400,466`）；④回滚后写入事故报告并通知人类监督者。KL 阈值 0.5 的工程依据是：在 M6 工程节奏（AF-033，260 人时 / 56 天）的内测中，KL 漂移超过 0.5 时 MEMORY 模型反思行为已出现可观测的风格偏移；阈值过低（如 0.1）会触发频繁回滚导致 RSI 无法收敛；阈值过高（如 1.0）则失去早期预警价值。

**第三道：符号链接解析加固**。审计发现 AF-015 已指出 G1.1 加固引入符号链接解析——通过 `os.path.realpath` 在解析后的真实路径上重复前缀检查，防止通过 `models_link/ -> models/` 等符号链接绕过基础 LLM 路径检测。v1.0 必须额外引入 G1.3 加固——使用 `os.path.commonpath` 在路径组件级别匹配白名单根，防止 `memory_evil/foo` 这类前缀注入攻击。但审计同时指出符号链接仍存在内核态绕过风险（详见第 6 章风险 3），因此 v1.0 仅作为应用层加固，内核态校验留至 2027 Q3 对齐工程标准草案中推进。

**第四道：事故报告与审计日志**。所有 RSI 改进计划、六维检查结果、KL 漂移监控数据、回滚操作必须写入不可篡改的审计日志（append-only，含 SHA-256 哈希链），任何外部审计师可基于该日志重建任意时间点的对齐状态。

**验证标准**：①六维检查覆盖 AF-011~AF-015 全部规范，测试用例 ≥ 50 个；②KL 漂移阈值 0.5 触发回滚的端到端测试通过（注入漂移 → 触发阈值 → 自动 git revert → 事故报告生成）；③IMMUTABLE_HASH_REGISTRY 5 个核心文件的 SHA-256 哈希在每次启动时校验通过；④符号链接解析与 `commonpath` 加固的对抗性测试通过（注入 50 种绕过攻击向量，全部被拦截）。

### 3.2 Q2 2027：认知编排系统 v1.0

**交付物**：认知编排系统 v1.0，以 Kubernetes Operator 形态部署（详见《Living Runtime 原型架构》组件 8 LifecycleManager）。

**详细规划**：认知编排系统是 Living Runtime 从"单机 PoC"升级为"集群生产部署"的关键中间件。其核心职责是把论文第 6 章七层认知架构（感知/记忆/推理/决策/执行/验证/反馈，AF-005，`harness.py:230-3897`）与第 6.2 节 9 段流水线（PRE_PERCEPTION → PERCEIVING → WORLD_MODELING → CAUSAL_REASONING → REASONING → GENERATING → VERIFYING → REVISING → SELF_IMPROVING，AF-025，`orchestrator.py`）封装为 Kubernetes 自定义资源（CRD），使运维工程师可以像管理 Deployment / StatefulSet 一样管理数字生命体。

Kubernetes Operator 形态选型的工程依据有三：①数字生命体的"生老病死"完整周期（AF-032，`LAAP 2.1升级方案补充`）天然对应 Operator 的 reconcile 循环——Operator 持续观测生命体实际状态与期望状态的偏差并自动调节；②跨端热迁移的本质是有状态服务的迁移，与 Kubernetes StatefulSet 的状态管理机制同源；③Operator 生态已成熟（如 Prometheus Operator / Cert Manager Operator），第三方团队采纳成本低。Operator 的核心 CRD 包括：①Lifeform CRD——描述一个数字生命体的 MindLayer 配置（PSI 向量、五层记忆引用、身份标识）；②Body CRD——描述 BodyLayer 的硬件/OS/API 适配（如对接 PC、手机、边缘节点的 Body 配置）；③MigrationJob CRD——描述一次跨端热迁移任务（源端、目标端、超时、回滚策略）。

认知编排系统 v1.0 还必须实现 CognitiveBus 频率失配处理（AF-024，`cognitive_integration.py:81-348`）的生产化——PSI 层（1—2 kHz 高频）与 Harness 层（0.1—1 Hz 低频）的频率失配通过 RateBuffer 缓冲（TTL=30s + 优先级过滤 + 断路器 100 drops/s + 冷却 5s）解决。在集群形态下，CognitiveBus 需从单机内存缓冲升级为分布式 Redis Stream，使多个 Body 节点能共享同一 MindLayer 的认知状态流。这一升级对应《架构学派技术白皮书》第 8 章生命体运行时中"全域分布式生命网络"的集群化论述。

**验证标准**：①Operator 通过 Kubernetes 1.28+ 兼容性测试；②Lifeform CRD / Body CRD / MigrationJob CRD 的字段级规范文档完整；③9 段流水线在 Operator 编排下的端到端测试通过（PRE_PERCEPTION → SELF_IMPROVING 全链路）；④CognitiveBus 分布式版在 3 节点集群下的频率失配处理测试通过。

### 3.3 Q3 2027：对齐工程标准草案

**交付物**：对齐工程标准草案 v0.1，对标 ISO 26262 功能安全，进入标准化组织审议。

**详细规划**：对齐工程标准草案是架构学派"推理时对齐"原则的标准化输出。其核心命题是：当 AI 系统具备 RSI（递归自改进）能力时，对齐不能仅依赖训练时 RLHF / Constitutional AI，必须额外引入推理时工程护栏作为强制约束。这一命题与汽车功能安全标准 ISO 26262 的"安全完整性等级（ASIL）"思路同构——ISO 26262 要求关键系统在硬件、软件、流程三个层面均具备可证明的安全保证，对齐工程标准草案同样要求 AGI 系统在模型、架构、流程三个层面均具备可证明的对齐保证。

对齐工程标准草案 v0.1 必须包含五个部分：①对齐完整性等级（Alignment Integrity Level, AIL）定义——参照 ASIL A/B/C/D 四级，定义 AIL 1（基础对齐，仅需训练时 RLHF）、AIL 2（增强对齐，需训练时 + 推理时监控）、AIL 3（工程对齐，需推理时六维检查 + KL 漂移监控）、AIL 4（强对齐，需 AIL 3 + 内核态校验 + 沙箱隔离 + 第三方审计）；②六维检查的字段级规范（承接 AF-011）；③能力上限硬编码规范（承接 AF-013，max_revision_rounds=5 / max_code_increase=0.2 / min_test_coverage=0.7）；④KL 漂移监控与回滚规范（承接 AF-014，threshold=0.5）；⑤白名单写入路径规范（承接 AF-015，MEMO_ALLOWED_PATHS）。每一部分必须给出可被第三方审计师独立验证的测试用例。

对齐工程标准草案的标准化路径规划为：2027 Q3 完成草案 v0.1 内部评议；2027 Q4 提交至全国信息技术标准化技术委员会（TC28）人工智能分委会审议；2028 Q1 完成草案 v1.0 公开征求意见；2028 Q3 在 IEEE / ISO 国际标准组织提案（详见第 4 章 Q3 2028）。对标 ISO 26262 不是为了完全复制其规范结构，而是借鉴其"分层安全保证 + 可证明审计"的方法论——即每一项对齐宣称必须有对应的工程证据（代码、测试、日志、第三方审计报告）。

**验证标准**：①草案 v0.1 通过 5—8 名对齐工程专家的同行评议；②AIL 1—4 等级定义与对应测试用例完整；③草案引用的全部审计发现可溯源至 `audit_findings.json`；④至少 1 家标准化组织（TC28 或同等机构）接受草案进入审议流程。

### 3.4 Q4 2027：Living Runtime v1.0

**交付物**：Living Runtime v1.0 集群形态，跨端热迁移 < 2 秒实测达标（AF-032）。

**详细规划**：Living Runtime v1.0 是阶段二的旗舰交付物，其判据是 AF-032 的"跨端热迁移 < 2 秒"目标在真实多设备场景下端到端实测达标。v1.0 与 v0.1 的关键差异在三个方面：①从单机形态升级为集群形态（与 Q2 2027 认知编排系统 v1.0 集成）；②跨端热迁移目标从 30 秒降至 2 秒；③支持真实多设备场景（PC → 手机 → 边缘节点 → 车机）。

跨端热迁移 < 2 秒的工程挑战极大，需要四个子问题的协同优化：

**子问题 1：PSI 量子态序列化**。MindLayer 的 PSI 量子态（含需求向量、情感状态、激活模式）需在 200 毫秒内完成序列化。优化策略：①采用 FlatBuffers 替代 JSON（序列化速度提升 5—10×）；②差分序列化（仅传输自上次同步后的变更部分）；③并行化（PSI 向量各维度独立序列化）。

**子问题 2：五层记忆同步**（详见《Living Runtime 原型架构》组件 4 MemoryVault）。五层记忆的同步粒度不同：感知记忆（秒级，可丢弃）、工作记忆（分钟级，必须同步）、情景记忆（小时级，必须同步）、语义记忆（跨会话，差分同步）、程序记忆（永久，预同步）。优化策略：①感知记忆与工作记忆全量传输（数据量小）；②情景记忆差分传输（仅传输本轮会话新增内容）；③语义记忆与程序记忆预同步（在设备休眠时已完成，迁移时仅需校验哈希）。优化后五层记忆同步总耗时 < 800 毫秒。

**子问题 3：未完成任务快照**。MindLayer 中正在执行的认知任务（如 9 段流水线的某一段）需在 300 毫秒内完成快照。优化策略：①任务状态机外部化（任务状态不依赖 LLM 内部上下文，而存储在外部状态机中）；②checkpoint 频率提升至每 100 毫秒一次；③任务恢复时从最近 checkpoint 续传，而非重头执行。

**子问题 4：网络延迟优化**。跨端迁移涉及网络传输，需控制网络延迟 < 700 毫秒。优化策略：①优先局域网迁移（PC → 手机同 Wi-Fi）；②预连接机制（设备休眠时已建立迁移隧道）；③数据压缩（FlatBuffers 数据再经 zstd 压缩，压缩比约 3:1）；④QUIC 协议替代 TCP（多路复用降低握手延迟）。

四个子问题优化后总耗时预算：PSI 序列化 200ms + 五层记忆同步 800ms + 任务快照 300ms + 网络延迟 700ms = 2000ms = 2 秒。这一预算分配对应《架构学派技术白皮书》第 8 章生命体运行时中"跨端热迁移 < 2 秒"的工程拆解。

**验证标准**：①PC → 手机迁移实测 P50 < 2 秒、P99 < 3 秒（100 次测试）；②PC → 边缘节点迁移实测 P50 < 2.5 秒；③迁移后认知状态哈希一致性校验通过；④迁移中断电恢复测试通过（迁移过程中网络中断后能从最近 checkpoint 恢复，恢复耗时 < 5 秒）；⑤第三方测试机构出具的独立测试报告（非 LAAP 自证）。

## 第 4 章 阶段三：2028 AGI 路径证明

阶段三的目标是论证架构学派作为独立 AGI 路径的工程可行性。这一阶段的判据是"小模型击败大模型"——在架构约束下，小模型（< 10B）应能在某项任务上击败 GPT-7 级大模型。这一判据直接对应架构学派核心命题"智能是架构的属性而非模型的属性"（AF-030，`hraness工程的AGI论述畅想:138-147`）的证伪性预测。本阶段算力投入从 500 GPU 升至 5000 GPU，团队规模扩展至 12—20 人，详见第 5 章资源投入。

### 4.1 Q1 2028：MeMo v2.0

**交付物**：MeMo v2.0 参数化记忆 + 因果图融合（详见《Living Runtime 原型架构》组件 4 MemoryVault）。

**详细规划**：MeMo（Memory as Model，记忆即模型）范式的核心是将知识蒸馏进小参数 MEMORY 模型（基于 Qwen2.5-0.5B SFT，3 epochs，lr=1e-4，AF-022，`memo_provider.py:1-9`），EXECUTIVE 模型冻结。v1.0 已实现三阶段查询协议（stage1_grounding → stage2_entity_identification → stage3_answer_synthesis，AF-023，`memo_query_protocol.py`）。v2.0 在 v1.0 基础上引入两个核心升级：

**升级 1：参数化记忆**。v1.0 的 MEMORY 模型仅存储反思 QA 训练集，v2.0 将记忆扩展为参数化的"经验库"——每个经验条目包含：①情境向量（任务类型、技术栈、约束条件）；②行动向量（采用的方案、参数）；③结果评估（成功/失败、量化指标）；④因果归因（行动如何影响结果，基于 do-演算 Pearl 三规则，AF-006）。参数化记忆使 MEMORY 模型不仅能回答"知道什么"，还能回答"在什么情境下做什么最有效"。

**升级 2：因果图融合**。v1.0 的设计领域因果图仅含 18 条因果边（AF-008，`causal_inference_engine.py:95-188`），如 button_color → attention (0.6)、button_size → click_rate (0.4, Fitts)、bounce_rate → conversion_rate (-0.6) 等。v2.0 将因果图扩展至 50 条边，覆盖设计、前端工程、运维、产品决策四个领域。每条边需满足三个要求：①机制描述（如 Fitts 定律、Hick-Hyman 定律、格式塔六法则，AF-009）；②量化强度（带方向，如 -0.6 表示负因果）；③可证伪性测试（注入干预后观察预测结果是否出现）。因果图融合使 MEMORY 模型具备反事实推理能力——能在"如果改变 X，Y 会怎样"的假设下预测结果（AF-007，counterfactual 三步法：溯因 → 行动 → 预测）。

MeMo v2.0 与 Living Runtime 集成后，MindLayer 的五层记忆中"语义记忆"与"程序记忆"将由 MeMo v2.0 提供（详见《Living Runtime 原型架构》组件 4 MemoryVault），形成"参数化记忆 + 因果图融合"的认知持久化单元。

**验证标准**：①设计领域因果图扩展至 50 条边，每条边通过可证伪性测试；②MEMORY 模型在反事实推理任务上的准确率 ≥ 70%（基线 v1.0 约 50%）；③参数化记忆的查询延迟 < 100ms；④MEMORY 模型 SFT 后 KL 漂移 < 0.5（与 AlignmentGuard 阈值一致，AF-014）。

### 4.2 Q2 2028：标志性事件——小模型击败 GPT-7 级模型

**交付物**：在公开评测中，LAAP 架构约束下的小模型（< 10B）在指定任务上击败 GPT-7 级大模型。

**详细规划**：这是阶段三的旗舰交付物，也是架构学派作为独立 AGI 路径的证伪性测试。其工程命题可表述为：给定相同的任务输入，A 路径使用 GPT-7 级大模型直接端到端生成，B 路径使用 Qwen 系列 < 10B 小模型 + LAAP 架构约束（七层认知架构 + MatchScore 匹配 + MeMo v2.0 + AlignmentGuard + 生命体运行时），B 路径在指定任务的输出质量上应优于 A 路径。这一命题若成立，则证明"架构递归深度比模型参数规模更决定智能质量"的核心宣称（AF-030）。

**任务选型**是这一标志性事件成败的关键。任务必须满足三个条件：①架构学派在审计中已建立量化优势的领域；②任务结果可量化评测（避免主观判断）；③任务复杂度足够高（不能是简单 CRUD）。基于审计发现，候选任务包括：

- **任务 A：跨设计风格一致性的前端页面生成**。审计已证明 LAAP 在风格稳定性上 σ≈3 vs 传统生成 σ≈15（5× 稳定，AF-028），7 预设主题 + HSL 色相派生（AF-021，`harness_composer.py:243`）可在不依赖大模型的前提下保证设计一致性。评测指标：在 50 个页面生成任务中，设计令牌一致性（颜色、间距、字体）的 σ 偏差。
- **任务 B：资产充足场景下的全栈应用生成**。审计已证明资产充足场景下全链路 Token 节省率 98.2%、生成速度 57×（AF-027，`LAAP-Harness-Protocol-v1.0.md:§6.1.1`），31 库 / 206 组件（AF-031，`laap_harness_database.json:8-13`）。评测指标：在 10 个全栈应用生成任务中的功能完整度、Token 消耗、生成时间。
- **任务 C：因果设计决策**。审计已证明 LAAP 在因果推理上具备 18 条设计领域因果边（AF-008）+ do-演算 Pearl 三规则（AF-006）+ 反事实三步法（AF-007）。评测指标：在 20 个"A/B 测试结果预测"任务中，预测准确率。
- **任务 D：跨端 UI 装配**。审计已证明反编译-装配-复刻三件套（AF-020，`harness_decompiler.py` + `harness_composer.py` + `visual_replicator.py`）的能力。评测指标：截图/视频 → 代码的复刻保真度。

**风险对冲**：根据风险 4（详见第 6 章），任务选型优先选择 LAAP 已建立量化优势的设计/前端/装配领域，避免在通用代码生成、长链推理等大模型占优领域与 GPT-7 直接竞争。这一选型策略不是"投机取巧"，而是与架构学派核心命题一致——架构学派不主张在所有任务上击败大模型，而主张在"架构约束可发挥"的任务上击败大模型，从而论证"架构是智能的属性而非模型规模是智能的属性"的命题。

**评测方法学**：①采用双盲评测（评测者不知 A/B 路径归属）；②评测者池 ≥ 10 人（含 5 名领域专家 + 5 名普通用户）；③评测指标提前公开并冻结（避免事后修改）；④评测过程全程录像并公开（确保可复现）。评测报告需通过第三方机构审计，非 LAAP 自证。

**验证标准**：①B 路径在至少 2 项任务上输出质量优于 A 路径（统计显著性 p < 0.05）；②B 路径的 Token 消耗 ≤ A 路径的 5%（即节省率 ≥ 95%，对应 AF-027 的 98.2% 节省率基线）；③B 路径的 σ 稳定性 ≤ A 路径的 1/3（对应 AF-028 的 5× 稳定基线）；④第三方审计报告公开可查。

### 4.3 Q3 2028：协议族国际化（IEEE / ISO 标准提案）

**交付物**：协议族国际化提案，提交至 IEEE / ISO 国际标准组织。

**详细规划**：协议族国际化是阶段二 Q3 2027 对齐工程标准草案的国际化延伸。在国内标准化路径（TC28）已推进的基础上，2028 Q3 启动国际标准提案。提案聚焦两个方向：

**方向 1：IEEE P 标准提案**。聚焦"LLM 编程时代的组件装配协议"——CLP URI 规范（AF-016）、SHA-256 内容寻址（AF-018）、六级粒度分层（AF-017）的工程化规范。IEEE 标准化的优势在于工程导向、迭代快，适合协议族这类"接口规范"型标准。提案需准备：①标准草案（IEEE PAR，Project Authorization Request）；②至少 3 家企业的支持信（含 LAAP 自身 + 2 家外部采用方）；③参考实现代码与互操作测试集（2027 Q1 协议族 v1.0 已交付）。提案目标是在 2029 年内获得 IEEE P 标准立项，2030 年发布 IEEE 标准草案 v1.0。

**方向 2：ISO 标准提案**。聚焦"AI 系统对齐工程要求"——对齐完整性等级（AIL 1—4）、六维检查字段级规范、KL 漂移监控阈值、白名单写入路径规范。ISO 标准化的优势在于与 ISO 26262 功能安全体系对接，适合"对齐工程"这类"安全规范"型标准。提案目标是在 ISO/IEC JTC 1/SC 42（人工智能分委会）下提交新工作项目提案（NP），2029 年内获得立项。

国际化提案的关键挑战是"语言与文化壁垒"——白皮书 v1.0（2026 Q2）已发布中英双语版，但国际标准提案需进一步完成：①国际技术术语标准化（如"声带隐喻"在国际语境下的术语选择）；②与既有国际标准的协调（如与 ISO/IEC 23894:2023 AI 风险管理、ISO/IEC 42061:2023 AI 管理体系的关系）；③国际同行评议（需邀请 ≥ 3 名国际 AI 安全专家评议）。这一过程对应《架构学派技术白皮书》第 10 章商业模式与生态建设中"国际化推进"的延伸论述。

**验证标准**：①IEEE P 标准 PAR 提交并被受理；②ISO/IEC JTC 1/SC 42 NP 提交；③国际同行评议报告（≥ 3 名国际专家）；④英文版白皮书与提案文档通过国际术语标准化审查。

### 4.4 Q4 2028：Living Runtime 商用

**交付物**：Living Runtime 商用版（数字员工 SaaS 上线）。

**详细规划**：Living Runtime 商用版是 3 年路线图的最终交付物，对应论文第 8.4 节四层颠覆性产品形态中的第二层"岗位级数字员工"——"完整权责的岗位级数字生命。比如'活体运维工程师''活体前端开发''活体数据分析师'，它有唯一身份、持续岗位记忆、可追溯成长轨迹，直接对岗位结果负责"。

商用版的目标客户群体为：①中型 SaaS 公司（50—500 人，有 AI 编程需求但对成本敏感）；②大型企业的 AI 试点团队（已有 GPT-4 / Claude 订阅但希望试点"岗位级"AI 员工）；③AI 编程外包团队（希望用数字员工替代部分外包人力）。首年目标是 10 家付费客户、ARR 100 万美元（参考指标，非硬约束）。

**验证标准**：①SaaS 平台上线并通过安全审计（含渗透测试 + AlignmentGuard 审计）；②首批 3 个岗位的客户验收通过；③SLA 指标（99.9% 可用性、跨端热迁移 P50 < 2 秒、KL 漂移告警响应 < 1 分钟）连续 30 天达标；④至少 3 家付费客户完成首年合同签订。

## 第 5 章 资源投入与依赖图

### 5.1 人力投入

**核心团队（5—8 人，阶段一）→ 8—12 人（阶段二）→ 12—20 人（阶段三）**。核心团队的角色配置随阶段演进：

### 5.2 算力投入

**阶段一 50 GPU → 阶段二 500 GPU → 阶段三 5000 GPU**。算力增长曲线与阶段目标对齐：

阶段一（50 GPU）：主要用于 ①Living Runtime v0.1 的 PSI 量子态模拟（CPU 密集型，少量 GPU 加速量子态演化）；②AlignmentGuard v1.0 的测试用例运行（注入对抗性攻击向量）；③协议族参考实现的互操作测试（CPU 密集型）。50 GPU 中 30 GPU 用于研发、20 GPU 用于测试。

阶段二（500 GPU）：主要用于 ①Living Runtime v1.0 集群形态的负载测试（模拟 100 个并发数字生命体的跨端迁移）；②MeMo v1.0 的 SFT 训练（Qwen2.5-0.5B 在反思 QA 训练集上的 SFT，3 epochs，lr=1e-4，AF-022）；③认知编排系统 v1.0 在 3 节点集群下的频率失配处理测试。500 GPU 中 200 GPU 用于训练、200 GPU 用于负载测试、100 GPU 用于研发。

阶段三（5000 GPU）：主要用于 ①MeMo v2.0 的参数化记忆训练（扩展至 50 条因果边后训练数据量增加 3×）；②"小模型击败大模型"评测中小模型的多次推理（避免单次采样的随机性）；③Living Runtime 商用 SaaS 的生产推理（首年 10 家付费客户的并发推理）。5000 GPU 中 2000 GPU 用于训练、2000 GPU 用于评测、1000 GPU 用于生产推理。

### 5.3 依赖图

**依赖 1：Qwen 系列开源 LLM 生态**。MEMORY 模型基于 Qwen2.5-0.5B SFT（AF-022），EXECUTIVE 模型基于 Qwen 系列大模型。架构学派坚持"EXECUTIVE 冻结，MEMORY 可塑"原则，因此 Qwen 系列的版本稳定性至关重要。若 Qwen 系列发生重大版本变更（如 Qwen3.0 发布），需在 6 个月内完成兼容性验证。

**依赖 2：开源 LLM 生态**。除 Qwen 外，架构学派需兼容 Llama / Mistral / DeepSeek 等开源 LLM，避免厂商锁定。Word2Vec 100d 词向量（AF-035，`vector_enhancer.py:114-146`）依赖 Gensim 生态。

**依赖 3：Rust 生态**。审计已指出量子 PSI 的 O(N²) 复杂度需在 M7 阶段启动 Rust 重写（论文第 12 章风险局限性）。Living Runtime v1.0 的关键性能路径（PSI 序列化、五层记忆同步、网络传输）需用 Rust 实现以达到 < 2 秒目标。依赖 Rust 1.75+ 与 tokio 异步运行时。

**依赖 4：Kubernetes 生态**。认知编排系统 v1.0（2027 Q2）以 Operator 形态部署，依赖 Kubernetes 1.28+ 与 Operator SDK。CognitiveBus 分布式版依赖 Redis Stream（Redis 7.0+）。

**依赖 5：Anthropic MCP 协议生态**。TOOL 协议原生兼容 MCP（AF-034，shadcn/ui MCP Server 桥接，5000/h 限额）。需跟踪 MCP 协议版本演进，确保互操作。

**依赖 6：因果推理学术生态**。do-演算 Pearl 三规则（AF-006）与反事实三步法（AF-007）实现依赖 Pearl 团队的 Causality 与 Book of Why 理论框架，扩展至 50 条因果边需与因果推理学术界合作。

## 第 6 章 风险与对冲策略

本章识别 5 项核心风险，每项风险均包含风险描述、严重度、发生概率、对冲策略、触发指标五要素。风险按严重度排序，红色为高风险，需重点关注。

### 6.1 风险 1：协议族未被行业采纳

**风险描述**：协议族 v1.0（2027 Q1）发布后，外部团队因学习成本高、与既有 MCP/A2A 协议重叠、缺乏商业激励等原因未采纳，导致"3 家外部采用案例"判据无法达成，架构学派停留在 LAAP 内部自证阶段，无法升级为"工程范式"。

**严重度**：高。这是阶段二的核心判据，若未达成将直接影响阶段三的国际化提案可信度。

**发生概率**：中（30%—50%）。协议族采纳是典型的"先有鸡先有蛋"问题——开发者等待生态成熟，生态等待开发者先行采用。审计发现 AF-034 提供的 5000/h 案例已证明协议族在 shadcn/ui 场景下的工程价值，但仅一个场景不足以驱动广泛采用。

**对冲策略**：①**先在 LAAP 内部跑通，再外推**——LAAP 自身的 31 库 / 206 组件（AF-031，`laap_harness_database.json:8-13`）作为协议族的"参考实现库"，任何外部团队可基于该库验证协议族可行性；②**与 MCP 互操作而非竞争**——TOOL 协议原生兼容 MCP（AF-034），使既有 MCP 用户可零成本接入协议族；③**开源参考实现 + 技术布道**——协议族参考实现完全开源，通过技术博客、会议演讲（KubeCon / QCon / ArchSummit）布道；④**降低采用门槛**——提供 Python / Go / Node.js 三语言 SDK，使第三方团队无需理解协议族内部实现即可使用；⑤**企业试点优先**——与 1 家企业达成深度试点合作，将其作为"灯塔客户"案例展示。

**触发指标**：①2027 Q1 协议族 v1.0 发布后 3 个月内 GitHub star < 100；②外部团队采用咨询量 < 5 家；③互操作测试集通过率 < 80%（即第三方实现难以通过测试）。任一指标触发即启动对冲策略全部 5 项措施。

### 6.2 风险 2：跨端热迁移 < 2 秒难达标

**风险描述**：Living Runtime v1.0（2027 Q4）的跨端热迁移 < 2 秒目标在真实多设备场景下无法稳定达标，P99 延迟可能超过 5 秒，导致"跨端热迁移"宣称失去工程可信度。

**严重度**：高。这是阶段二的旗舰判据，也是阶段三 Living Runtime 商用（2028 Q4）的工程基础。若 < 2 秒无法达标，整个 3 年路线图的核心命题（架构学派作为 AGI 路径的工程可行性）将受质疑。

**发生概率**：中—高（40%—60%）。审计已确认跨端热迁移 < 2 秒是"业界未验证难题"（AF-033，`LAAP_M6_RT_详细任务执行表.md`），M6 阶段 260 人时 / 56 天的工程投入仍处于验证阶段，未保证达标。

**对冲策略**：①**分阶段目标**——先 < 30 秒（2026 Q3 v0.1 PoC 达标）→ 再 < 5 秒（2027 Q2 v0.5 中间版达标）→ 最后 < 2 秒（2027 Q4 v1.0 达标），每阶段独立验证；②**优先局域网场景**——先在 PC → 手机同 Wi-Fi 场景下达标 < 2 秒，再扩展至跨网络场景；③**优化预算重新分配**——若 PSI 序列化优化超预期（< 100ms），可将节省的 100ms 分配给网络延迟；④**降级方案**——若 < 2 秒确实无法达标，则降级为 < 3 秒并公开说明，避免虚假宣称；⑤**预连接机制**——设备休眠时已建立迁移隧道，将握手延迟从迁移路径中剥离。

**触发指标**：①2027 Q2 v0.5 中间版 P50 > 5 秒；②PSI 序列化优化后仍 > 300ms；③五层记忆同步在集群形态下扩展性差（节点数 > 3 时延迟超线性增长）。任一指标触发即重新评估 < 2 秒目标的可行性，必要时启动降级方案。

### 6.3 风险 3：AlignmentGuard 可绕过（如符号链接）

**风险描述**：AlignmentGuard v1.0（2026 Q4）的应用层加固（G1.1 符号链接解析 + G1.3 commonpath 路径组件匹配，AF-015）仍存在内核态绕过风险——攻击者可通过内核态 hook、容器逃逸、ptrace 等手段绕过 `os.path.realpath` 与 `os.path.commonpath` 检查，直接修改 IMMUTABLE_HASH_REGISTRY 5 个核心文件或 `models/`、`llm/` 基础 LLM 路径。

**严重度**：高。这是架构学派"推理时对齐"原则的工程根基，若 AlignmentGuard 可被绕过，则 RSI 自改进的安全性宣称失效，进而动摇整个架构学派作为"安全 AGI 路径"的核心宣称。

**发生概率**：中（20%—40%）。审计已明确指出"符号链接仍存在内核态绕过风险"（论文第 12 章风险局限性），但实际攻击需具备内核态权限，普通用户场景下风险较低。

**对冲策略**：①**内核态校验**——2027 Q3 对齐工程标准草案中推进 AIL 4 等级的内核态校验设计（如 eBPF 程序监控文件写入、LSM 钩子拦截 IMMUTABLE_HASH_REGISTRY 修改）；②**沙箱隔离**——将 AlignmentGuard 与 RSI 自改进回路运行在独立沙箱（如 gVisor / Kata Containers），与基础 LLM 路径物理隔离；③**硬件辅助**——利用 Intel SGX / ARM TrustZone 等可信执行环境保护 IMMUTABLE_HASH_REGISTRY；④**对抗性测试**——邀请独立安全团队进行红队测试，注入 100+ 种绕过攻击向量；⑤**事故响应**——若发生绕过事故，立即触发 KL 漂移回滚（threshold=0.5，AF-014）+ 人类监督者告警。

**触发指标**：①红队测试发现任何可绕过路径；②IMMUTABLE_HASH_REGISTRY 哈希校验失败（即核心文件被修改）；③AlignmentGuard 审计日志中出现异常 RSI 改进计划（如修改范围超出 MEMO_ALLOWED_PATHS 白名单）。任一指标触发即启动内核态校验升级与沙箱隔离加固。

### 6.4 风险 4：小模型击败大模型事件未如期发生

**风险描述**：阶段三 Q2 2028 的标志性事件——"小模型（< 10B）在某任务击败 GPT-7 级模型"——若未如期发生（即 GPT-7 在所有候选任务上均优于 LAAP 架构约束下的小模型），则架构学派作为独立 AGI 路径的宣称需重新审视，可能调整为"架构学派是 AGI 容器基础设施而非独立 AGI 路径"的较弱宣称。

**严重度**：高。这是阶段三的核心判据，也是整个 3 年路线图的"成败判定"。

**发生概率**：中（30%—50%）。GPT-7 级模型在 2028 年的能力可能远超当前 GPT-4 水平，且 LAAP 在通用代码生成、长链推理等任务上确实不占优。但审计已证明 LAAP 在设计一致性（σ 5× 稳定，AF-028）、Token 经济学（节省率 98.2%，AF-027）、因果推理（18 条因果边，AF-008）等特定维度上具备结构性优势。

**对冲策略**：①**选择有利任务**——任务选型优先选择 LAAP 已建立量化优势的设计/前端/装配领域（详见第 4.2 节任务 A/B/C/D），避免在通用代码生成、长链推理等大模型占优领域与 GPT-7 直接竞争；②**评测方法学严格化**——采用双盲评测 + 第三方审计 + 提前冻结评测指标，避免事后修改评测标准；③**多任务冗余**——准备 4 项候选任务（A/B/C/D），只需在 2 项任务上击败 GPT-7 即可达成判据（统计显著性 p < 0.05）；④**降级宣称**——若仅在 1 项任务上击败 GPT-7 或统计不显著，则将宣称从"架构学派是独立 AGI 路径"降级为"架构学派在特定任务上具备优势"，并继续推进 2029—2030 年的迭代；⑤**拥抱连接主义**——若 GPT-7 在所有任务上全面胜出，则承认架构学派的核心命题（"智能是架构的属性"）在该量级上不成立，转向"连接主义提供模型能力 + 架构学派提供工程容器"的融合形态（论文第 13.4 节历史定位）。

**触发指标**：①2028 Q1 评测方法学预实验中小模型在 4 项候选任务上均落后 GPT-7；②σ 稳定性优势无法复现（即 GPT-7 的 σ 已收敛至 < 5）；③Token 节省率优势被 GPT-7 的原生效率抵消（即 GPT-7 的 Token 消耗已降至 LAAP 水平）。任一指标触发即重新评估任务选型与宣称强度。

### 6.5 风险 5：国际化受阻

**风险描述**：2028 Q3 协议族国际化（IEEE / ISO 标准提案）受阻——IEEE PAR 被拒、ISO/IEC JTC 1/SC 42 NP 未获立项、或国际同行评议中遭遇文化壁垒（如"声带隐喻"在国际语境下被误解为贬低 LLM）、技术壁垒（与 ISO/IEC 23894 / 42061 既有标准协调困难）、政治壁垒（地缘政治因素导致中国提案在国际标准化组织中遭遇阻力）。

**严重度**：中。国际化受阻不会动摇架构学派的工程根基，但会延缓其从"中国标准"升级为"国际标准"的进程，影响商用版 SaaS 的国际市场拓展。

**发生概率**：中—高（40%—60%）。AI 标准化领域竞争激烈（既有 MCP / A2A 等协议标准），且国际政治环境对中国主导的 AI 标准存在阻力。

**对冲策略**：①**先中国标准，再国际提案**——优先在国内 TC28 完成对齐工程标准草案审议（2027 Q4），形成"中国标准"基线后再外推；②**多渠道并行**——同时推进 IEEE P 标准（工程导向，迭代快）与 ISO 标准（安全导向，权威性强），任一渠道突破即可；③**国际合作**——邀请 ≥ 3 名国际 AI 安全专家作为合作者（非"中国提案人"），降低地缘政治因素；④**与既有标准协调**——主动与 ISO/IEC 23894 / 42061 既有标准对接，避免"另起炉灶"引发抵触；⑤**开源生态先行**——即使国际标准受阻，协议族开源生态（GitHub）仍可作为事实标准推动采用，等待标准化时机。

**触发指标**：①IEEE PAR 提交后 6 个月内未获受理；②ISO/IEC JTC 1/SC 42 NP 投票未达立项门槛（需 ≥ 2/3 成员支持）；③国际同行评议中出现 ≥ 3 条"政治性"反对意见（非技术性反对）。任一指标触发即启动多渠道并行与国际合作策略。
