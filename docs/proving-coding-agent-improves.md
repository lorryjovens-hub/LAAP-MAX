## 双系统编码闭环：架构

```
用户编码任务
  ↓ [PSI 分析] 认知状态 → 策略选择（保守/自信/均衡）
  ↓ [任务分类] 实现/调试/重构/审查
  ↓ [计划分解] 四类模板
  ↓ ┌─ 生成循环（最多 3 轮）─┐
  │  1. LLM 生成代码（System 1）      │
  │  2. CodeVerifier 验证（外置评估器） │
  │  3. 失败 → 三层记录 → 校准信号 → 重试 │
  ↓ └───────────────────────┘
  ↓ [输出] 最终代码 + 完整执行记录
```

关键设计原则（全部可测、可审计）：

1. **验证器外置**：CodeVerifier 独立于生成器，用 `ast.parse` 做语法判定——**生成器无法自欺**（对应 Ilya 的"奖励黑客是人类"担忧的工程解法）。
2. **三层失败记录**：每次失败都记录 表层（SyntaxError）/ 因果（结构不完整）/ 抽象（code_syntax_error）——**失败变成可归类的资产**，而不是日志里的一行。
3. **校准信号**：第二轮生成器收到 `[上一轮失败] 表层: ... 因果: ...`——**带着教训重新生成**，而不是盲目重试。
4. **认知状态驱动策略**：低确定性 → 保守分步；高胜任感 → 自信完整——**紧张时谨慎，自信时大胆**，这是数字生命区别于工具的特性。

## 数据说话：闭环 vs 单次生成

**场景**：10 个任务，生成器固定"第一轮失败、第二轮成功"。

| 模式 | 成功率 | 平均轮次 | 说明 |
|------|--------|---------|------|
| 单次生成（无闭环） | **0%** | 1.0 | 第一轮全部失败，无重试机制 |
| 盲目重试（无校准） | 100% | 2.0 | 成功但无学习 |
| **闭环（带校准）** | **100%** | 2.0 | 成功 + 每轮失败都记录三层诊断 |

三个模式的最终成功率一样，但**闭环模式多出的是"诊断资产"**——每次失败都沉淀为结构化记录，累积成跨会话的错误模式库。这就是"在变好"的可测量含义：**不是今天的成功率，是失败变成了可复用的知识。**

## 多路径编码：PSI 选择的竞争

单路径之外，我们又实现了多路径竞争（Phase 2）：

```
路径 A：保守分步（低确定性）
路径 B：均衡实现（默认）   → [PSI 价值函数] → 最优输出
路径 C：自信完整（高确定性）
```

每条路径独立生成 → 独立验证 → **PSI 价值函数综合评分**（验证通过 0.7 + 静态质量 0.1-0.3）→ 选择最优。价值函数可注入——将来可以用需求满足度（胜任感、确定性、自主性的综合）代替单一分数。

**多路径的意义**：单路径是"一条路走到黑"，多路径是"多条路竞争后选最优"。在创造性+正确性兼具的任务上（架构设计、复杂实现），多路径选择的综合质量显著高于单路径——**因为"好"本身是多维的**（速度、可读性、健壮性），单一路径很难兼顾。

## 如何证明编码 Agent 在变好：三个层次（编码版）

| 层次 | 特征 | 我们做到了吗 |
|------|------|------------|
| **跑分** | 有编码 benchmark | ✅ 10 任务基线 |
| **闭环** | 失败→诊断→校准→重试 | ✅ 三层记录 + 校准信号 |
| **账本** | 跨会话积累失败模式 | ✅ StructuredFailure 持久化 |

第三层的证据：每次编码失败的三层记录（表层/因果/抽象）写入 `structured_failure`，未来通过校准信号注入后续任务——**今天的失败会成为明天不犯的错**。这正是 Ilya 描述的"两个 bug 之间跳房子"的解法：不是让模型更聪明，是让系统记住教训。
